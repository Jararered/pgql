# Mass Gift in PGQL 0.1

Original implementation in `agent/modules/mass-gift.js`, `agent/core/gift-queue.js` and `agent/adapters/game-gifts.js`. It uses the game's own managed services, with no standalone network client, borrowed Pokemod agent or credentials. The injected menu generates action buttons from module metadata.

Enable **Mass Gift**, then choose **Preview friends and gifts**. **Send gifts** and **Open gifts** first show a fresh preview and a confirmation. **Cancel batch** stops before the next request; an already submitted operation must settle. **Batch status** shows counts; detailed progress is also in the controller log. Opening gifts consumes the normal daily allowance and adds rewards to the normal inventory. Sending consumes normal inventory gifts. The server's result remains authoritative.

The opening confirmation fetches paginated friend details and counts incoming gifts without opening them. The first implementation operates on the friend list returned by the game, deduplicates IDs and handles one action at a time. Sending advances available inventory only after success and reuses a still-available gift after a skipped friend. Opening prepares paginated friend details before reading incoming gifts. Daily opening limits, full bags, exhausted gifts and unknown results stop the batch. Requests have bounded waiting; uncertain outcomes are never automatically retried, and a timed-out request blocks another batch until it settles. The module does not create/delete postcards, remove friends or attach stickers.

Compatibility is gated to game version **0.433.0**. Metadata signatures and the three live services were observed on the connected phone. An original scheduler hooks `UnityEngine.UnitySynchronizationContext.ExecuteTasks` and drains work on the game thread; this avoids the bridge's default thread scheduler, which did not reach the callback in earlier tests. Types and method signatures are resolved at runtime; there are no copied native game offsets.

## Validation boundary

The runtime/action-schema, sequential queue, result-code handling, cancellation, busy guards, timeouts, preflight and retired-session lifecycle tests pass. The final APK was built, signed, installed and tested through its injected menu on rooted arm64 Android 17 with GO 0.431.0 / Unity 6000.3.21f1.

Live preview reported **82 friends, 33 sendable inventory gifts and 56 friends with an incoming gift**. This exercised service resolution, collection enumeration, managed promise callbacks, full-width retained handles, the paginated friend-detail request and incoming-gift lookup. Send/open confirmation dialogs rendered, and Cancel returned to settings without a batch beginning. The same game PID 27645 survived these checks and multiple reattachments after the lazy initialization change. Screenshots and logs are in `build/mass-gift-open-confirmation.png`, `build/mass-gift-preview.png` and `build/mass-gift-device-session.log`.

Earlier failed tests are preserved. Eager managed initialization intermittently preceded a native Niantic dispatch crash; the underlying dispatch cause was not proven. Deferring initialization allowed the final observed sessions to complete. The first adapter iterations also exposed getter casing, explicit-interface enumerators, string-based promise errors, and a 32-bit GC-handle binding on a runtime using full-width handles. The final adapter resolves exact metadata names, uses the observed Error(Action<string>) contract, validates retained handles against their target and frees them on a managed game frame. See `../analysis/native-instability-review.md` for the distinct native failure and control evidence.

**Actual gift sends and opens have not been executed in these tests.** Their RPC signatures were verified against live metadata and their queue/result behavior was tested with an adapter double; server effects and reward/cache updates remain unverified until a user-confirmed batch. Prolonged stability and other game versions are also unverified. Do not reattach while an outstanding gift request has an uncertain outcome; resident detach keeps inactive scripts and cannot recall a request already submitted to the game.

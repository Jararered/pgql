# Tamagotchi

## Current status

The care engine, module controls, adapter boundary and local tests are implemented.
**Live buddy interactions are not implemented yet.** There is no registered buddy
game profile, so enabling Tamagotchi reports that bindings are unverified and
sends no buddy requests. A no-op is never counted as a successful interaction.

The module is default-off. Its persistent switches select feeding, souvenirs,
play, snapshots and battles, plus permitted ordinary berry types. Battle is
default-off; Razz is the only initially permitted berry. Other settings do not
authorize Golden Razz, Silver Pinap or Poffin use.

The module checks once on enable and every 60 seconds. **Preview buddy care**
reports availability without exposing account/buddy identifiers. **Run / resume
care** performs a pass and resumes polling after a pause or failure. **Pause care**
stops future dispatch; already submitted operations may still settle. **Care
status** reports phase, counts, pending work and any failure reason.

Each pass checks souvenirs, up to three feed actions, play, snapshot and battle.
Before each action it reads a fresh snapshot. A changed buddy/session stops the
pass; unsupported, disabled or ineligible interactions are skipped. Repeated
snapshot keys cannot replay an action, even after disable/re-enable. The journal
is bounded at 4096 receipts and stops care when full. It persists only within
the current injected agent, not across game exits or fresh attachments.

Timeout or an unconfirmed result stops automatic care. A resource lease remains
held until the underlying request settles, preventing a new module instance from
overlapping it. Explicit resume does not erase the uncertain action's receipt.
The timer is an eligibility polling interval, not a claimed game cooldown.

## Required game adapter contract

After verification, register an original factory with
`PgqlGameAdapters.register('buddy', exactGameVersion, ctx => backend)`.
The game adapter reads the installed IL2CPP version before choosing the factory.
Unsupported versions fail rather than using the closest profile.

The backend must supply:

```js
snapshot(config) // Promise of a plain object
// {
//   ready: true,
//   identity: 'account + buddy + authoritative reward period',
//   actions: {
//     feed: { supported: true, eligible: true, key: 'stable eligibility key' },
//     souvenir: { supported: false, eligible: false, reason: '...' },
//     play: { supported: true, eligible: false },
//     snapshot: { supported: true, eligible: false },
//     battle: { supported: false, eligible: false }
//   }
// }
// Or { ready: false, reason: 'No buddy / map not ready / ...' }.

execute(action, { identity, key, config }) // Promise of { outcome, reason? }
// outcome: 'success' only for an acknowledged game result, or 'skipped'
// when a last-moment eligibility check prevents dispatch.
// Throw/reject for failures or any uncertain result.
```

Do not use timestamps generated by the poller as eligibility keys. Keys must
remain unchanged while the same opportunity remains visible, and change only
when the game confirms a new eligible opportunity. Feed keys must distinguish
acknowledged feeding progress; otherwise only one berry can be used per pass.

Before registering a profile, establish these contracts from game metadata and
observed results:

- Resolve buddy, account, authoritative daily progress and service readiness.
- Resolve and validate exact method signatures and result enums, not names alone.
- Run Unity work on the game thread and retain/release managed callbacks correctly.
- At dispatch, recheck the requested identity, action key, current progress and
  selected berry inventory. Refuse premium items and disallowed berry types.
- Read bag capacity and souvenir availability; only claim available souvenirs.
- Distinguish a server-confirmed interaction from an animation completion.
- Verify how battle participation is credited and when a battle is available.
  Do not fabricate participation or start a battle from an assumed enum value.
- Cancel undispatched work on disable; let in-flight promises settle without
  installing new hooks or resuming automation after teardown.

## Validation

Local suites exercise real core/module/adapter sources in a VM with explicit
mock backends. They cover all five action types, ordinary configuration, stale
keys, fresh identities, the three-feed bound, eligibility, cancellation,
disable/re-enable, uncertain outcomes, unsupported versions, preview privacy and
the unbound adapter's refusal to initialize the managed runtime.

On October 12, 2026, read-only metadata probing on the connected phone did not
produce buddy signatures. The first attachment timed out against background PID
18270. Foregrounding revealed a new PID, 23784. A probe attached to that process
and loaded its diagnostics module, then received a target-detached event
(`reason: 3`, `crashed: false`) before any metadata response. A subsequent PID
lookup found no running main game process. The cause of that exit is unknown;
this does not establish that the probe was safe or that any buddy interface works.
No feeding, souvenir, play, snapshot or battle calls were submitted.

Raw local observations are in `build/buddy-metadata*.jsonl`; these are ordinary
native-runner observations, not REA Evidence records. Further device probing was
stopped. The next integration step is to obtain and validate the buddy contract
on a stable session, implement the exact-version factory, then separately test
each interaction on-device. The current APK must not be described as providing
working automatic buddy care.
